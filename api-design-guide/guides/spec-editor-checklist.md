# Spec editor checklist

Use this as a review aid before submitting a BB specification. Tick an item when you have reviewed the applicable requirement or recommendation. Recommendations retain their `SHOULD` strength, and optional features need review only when used. Each item links to its governing rule; this list does not replace the full guide. [Rules by API kind](../rules-by-kind.md) identifies the rules applicable to your surface, including read-only APIs.

## Every specification

- [ ] `info` has a SemVer `version`, `title`, and useful `description`; `contact` is recommended when the contract is the right place for maintainer metadata. ([2.5](../part-a/2-openapi-document-standards.md#25-complete-info-block), [3.5](../part-a/3-asyncapi-document-standards.md#35-complete-asyncapi-info-block))
- [ ] `servers` is non-empty and meaningful: no `localhost`, no personal machines, no fake production domains; parameterised templates are recommended for reference specs. ([2.6](../part-a/2-openapi-document-standards.md#26-meaningful-servers-block), [3.6](../part-a/3-asyncapi-document-standards.md#36-servers-channels-operations-and-messages))
- [ ] Every operation has a stable `operationId` (or AsyncAPI operation key), its required contract references, and an accurate `description`; `summary` and tags are recommended when useful for navigation. ([2.7](../part-a/2-openapi-document-standards.md#27-complete-operation-metadata), [3.7](../part-a/3-asyncapi-document-standards.md#37-complete-asyncapi-operation-metadata))
- [ ] Add useful schema descriptions where names and structure do not make semantics clear. ([4.1](../part-a/4-documentation-requirements.md#41-useful-schema-descriptions))
- [ ] Enum values that are not self-explanatory are documented; representative request and response examples are recommended. ([4.2](../part-a/4-documentation-requirements.md#42-examples-for-bodies-and-enums))
- [ ] No placeholder text anywhere: no `TBD`, no `Lorem ipsum`, no `a, b, c`, no leftover content copied from another BB. ([4.3](../part-a/4-documentation-requirements.md#43-no-placeholder-text))
- [ ] Canonical surfaces are discoverable at the default paths or through a valid `api/index.yaml`; `api/coverage.yaml` traces exactly the active REQUIRED and RECOMMENDED requirements (excluding INAPPLICABLE requirements) using the dispositions in §4.6. DRAFT mappings are optional; active planned entries record gaps and prevent full conformance. ([4.5](../part-a/4-documentation-requirements.md#45-api-surface-inventory), [4.6](../part-a/4-documentation-requirements.md#46-functional-requirement-traceability))
- [ ] A security scheme is declared and applied to every operation by default, with per-operation overrides explicit. ([13.1](../part-d/13-authentication-and-authorisation.md#131-default-security-on-every-operation))
- [ ] `info.x-govstack-api-guide` pins exact guide and ruleset versions (`0.2.0-draft`) and every exception has all seven §20.3 fields: `rule`, `scope`, `rationale`, `record`, `reviewedBy`, `reviewedAt`, and `expiresAt`. ([20.3](../part-e/20-conformance-and-validation.md#203-declared-guide-conformance-version))
- [ ] The file passes its validator and the declared GovStack ruleset for applicable checks (see [Validating your spec](../guides/validating-your-spec.md)). ([20.1](../part-e/20-conformance-and-validation.md#201-every-file-passes-validation), [20.2](../part-e/20-conformance-and-validation.md#202-passes-the-govstack-spectral-ruleset))
- [ ] `info.version` identifies the published surface contract and agrees with any major version exposed in a path, channel, or protocol field. ([18.1](../part-d/18-compatibility-and-lifecycle.md#181-semver-versioning))
- [ ] Consistent `camelCase` is recommended for GovStack-owned JSON fields; fields imported from an external standard retain their standard spelling. Existing published fields follow the compatibility rules before any renaming. ([9.2](../part-c/9-json-conventions-and-naming.md#92-camelcase-field-names))
- [ ] Resource identifiers are strings, unique within their documented scope, and treated as opaque by clients. Stable source-owned identifiers are allowed; newly assigned IDs should be server-generated opaque values. URL identifiers are URL-safe and carry no personal data. ([10.1](../part-c/10-data-types-and-formats.md#101-opaque-server-generated-identifiers))

## REST surfaces (OpenAPI 3.1)

- [ ] The file declares a qualified OpenAPI 3.1 patch (`3.1.0`, `3.1.1`, or `3.1.2` for guide/ruleset `0.2.0-draft`). ([2.1](../part-a/2-openapi-document-standards.md#21-openapi-31-required))
- [ ] The canonical entrypoint is at the default `api/openapi.yaml` path or is listed in `api/index.yaml`; no legacy `api/swagger.yaml` or JSON copy is treated as canonical. ([2.2](../part-a/2-openapi-document-standards.md#22-one-canonical-openapi-entrypoint))
- [ ] Security schemes, parameters, headers, responses, and examples are local. If the four shared OpenAPI schemas are reused, the common file is vendored and version-pinned. ([2.8](../part-a/2-openapi-document-standards.md#28-conditional-vendored-openapi-schemas))
- [ ] Every non-local server and webhook URL uses HTTPS. Citizen-facing authorization follows §13.2, including its resource-server bearer option: access tokens rather than ID Tokens, PKCE for authorization-code clients, no password grant, and no implicit grant on new surfaces. ([13.2](../part-d/13-authentication-and-authorisation.md#132-oauth-and-oidc-for-citizen-operations), [13.7](../part-d/13-authentication-and-authorisation.md#137-protected-transport))
- [ ] The versioned HTTP surface exposes its major contract version unambiguously; `/v{N}/...` is recommended for new GovStack resource APIs. Recognised protocols may use their own version-negotiation mechanism. ([5.1](../part-b/5-url-structure-and-versioning.md#51-major-version-in-the-path))
- [ ] `/health` is unversioned, declares both `200` and `503`, returns `application/json` on `200`, and carries no citizen authentication. ([5.9](../part-b/5-url-structure-and-versioning.md#59-unversioned-health-endpoint))
- [ ] Only the standard unversioned endpoints claim the §5.10 exemptions; none declares a mutating method or hides a business resource under an exempt path. ([5.10](../part-b/5-url-structure-and-versioning.md#510-standard-unversioned-endpoints))
- [ ] No bulk-mutating or bulk-deleting operation can run against an entire collection with no selection parameter. ([6.7](../part-b/6-http-methods.md#67-bulk-mutation-needs-explicit-selection))
- [ ] Every operation declares every status code it can actually return; no operation declares only `200`. ([7.14](../part-b/7-http-status-codes.md#714-all-status-codes-declared))
- [ ] Input operations declare `400`; authenticated operations declare `401` with `WWW-Authenticate`; authorization failures declare `403` or the documented concealment use of `404`; operations addressing a specific resource declare `404`; every operation declares `500`. `409` is recommended where state conflicts apply and required for in-flight idempotency retries under [§14.5](../part-d/14-idempotency.md#145-key-reuse-and-fingerprint-mismatch). Completed creation uses `201` with `Location`; accepted work uses `202` plus an Operation. ([7.2](../part-b/7-http-status-codes.md#72-201-created-with-location)–[7.14](../part-b/7-http-status-codes.md#714-all-status-codes-declared))
- [ ] Every successful response body declares a concrete media type and schema; `204` declares no content. ([7.21](../part-b/7-http-status-codes.md#721-schemas-for-successful-response-bodies))
- [ ] Cross-service operations declare W3C `traceparent` and optional `tracestate`; error `traceId` maps to the W3C trace-id. ([8.4](../part-b/8-headers.md#84-w3c-trace-context-correlation))
- [ ] Error responses use `application/problem+json` (RFC 9457), use `https://govstack.global/problems/{bb-code}/{problem-slug}` as the sole machine identifier, and include `traceId`. They do not add `code` or `timestamp`. ([11.1](../part-c/11-errors.md#111-rfc-9457-problem-details)–[11.3](../part-c/11-errors.md#113-trace-identifier))
- [ ] Collection endpoints paginate unless their specification-fixed size is declared with `maxItems`. Bounded embedded arrays follow their representation contract without a separate Page envelope. Cursor pagination (`pageSize`, opaque `cursor`) is the default; `pageInfo.nextCursor` indicates continuation, even on an empty page. Admin or fixed-size lists may use offset pagination under [§12.6](../part-c/12-pagination-filtering-sorting.md#126-offset-pagination-envelope). ([12.1](../part-c/12-pagination-filtering-sorting.md#121-collections-must-paginate)–[12.3](../part-c/12-pagination-filtering-sorting.md#123-cursor-pagination-envelope))
- [ ] Every `202` response returns an Operation using a local schema and a `Location` that supports polling with `GET`. Documenting lifecycle, result, error, and polling semantics is recommended. Cancellation is optional; when supported it is documented and discoverable. ([15.1](../part-d/15-asynchronous-operations.md#151-202-with-operation-location)–[15.5](../part-d/15-asynchronous-operations.md#155-cancellation-via-cancel-sub-resource))
- [ ] POST endpoints covered by §14.1 require and accept `Idempotency-Key`, unless the resource contract already guarantees idempotency under §14.6. Naturally idempotent designs may omit the header; documenting their duplicate handling is recommended. ([14.1](../part-d/14-idempotency.md#141-idempotency-key-on-non-idempotent-posts), [14.6](../part-d/14-idempotency.md#146-naturally-idempotent-designs))
- [ ] Major version changes are visible through the declared versioning mechanism. Deprecated endpoints return `Deprecation` and a migration-documentation `Link`; `Sunset` is required when removal is planned. ([18.2](../part-d/18-compatibility-and-lifecycle.md#182-major-version-in-path-or-channel), [18.5](../part-d/18-compatibility-and-lifecycle.md#185-deprecation-and-sunset-headers))

## Event-driven surfaces (CloudEvents / AsyncAPI 3)

- [ ] For brokered transports and event streams, the file declares `asyncapi: 3.0.0` or `3.1.0` and lives at the default `api/asyncapi.yaml` path or is listed in `api/index.yaml`. HTTP push webhooks use OpenAPI under [§16.1](../part-d/16-cloudevents-and-webhooks.md#161-event-surfaces-documented). ([3.1](../part-a/3-asyncapi-document-standards.md#31-asyncapi-300-required), [3.2](../part-a/3-asyncapi-document-standards.md#32-one-canonical-asyncapi-entrypoint))
- [ ] Every domain event conforms to the CloudEvents envelope (`specversion`, `id`, `source`, `type`, domain payload under `data`). ([16.2](../part-d/16-cloudevents-and-webhooks.md#162-cloudevents-envelope-required))
- [ ] Event `type` values are stable, globally collision-resistant, include the registered BB code, and omit the API major version. Reverse-DNS naming is recommended for new GovStack event types. ([16.3](../part-d/16-cloudevents-and-webhooks.md#163-reverse-dns-event-types))
- [ ] AsyncAPI logical channel IDs are stable and their mapping to protocol-native addresses is documented. Versioned reverse-DNS IDs are recommended for new GovStack channels; addresses retain protocol-native syntax. ([17.2](../part-d/17-asyncapi-channel-rules.md#172-stable-logical-channel-ids-and-native-addresses))
- [ ] No logical channel ID, native address, topic, queue name, routing key, or channel parameter carries personal data. ([17.3](../part-d/17-asyncapi-channel-rules.md#173-no-personal-data-in-channels))
- [ ] Consumer-visible duplicate-handling, ordering, retention, and replay behaviour should be documented using standard protocol bindings where available. Deployment-internal capabilities may be omitted. ([17.11](../part-d/17-asyncapi-channel-rules.md#1711-duplicate-delivery-contract)–[17.15](../part-d/17-asyncapi-channel-rules.md#1715-no-universal-delivery-extensions))
- [ ] Representative AsyncAPI message examples are recommended where the schema alone does not make the interaction clear. ([17.20](../part-d/17-asyncapi-channel-rules.md#1720-representative-message-examples))

This checklist and artifact validation support specification review; they do not establish deployed implementation conformance or Building Block certification. See [Validating your spec](../guides/validating-your-spec.md) for the applicable mechanical checks.
